# Phase E — BR 확정 ★ 사람 판단 필수

**목적**: 분기 목록을 검증 가능한 Business Rule로 승격하거나 기각한다.
**주체**: AI가 제안, **사람이 판단**. 여기서 멈춘다.

이 Phase가 자동으로 통과되면 검증되지 않은 명세가 커밋된다. "이게 의도인가 버그인가"는 코드에 없는 정보이므로 AI가 원리적으로 판단할 수 없다.

**작업 전 `docs/br-criteria.md`를 반드시 읽을 것.**

---

## 프롬프트

```
[Phase C, D 결과]
<붙여넣기>

docs/br-criteria.md 의 판별 기준을 읽고 BR 초안을 작성해줘.
단, 확정이 아니라 제안이다.

각 BR 후보:
- 제안 ID: BR-<UC약어>-NNN
- 문장: 한 문장. "무엇을 보장하는가" 형식.
        구현 방식(싱글톤, 캐시 자료구조, 호출 순서) 언급 금지
- 근거: [이슈 #번호] / [기획서] / [git 이력] / [코드만]
- 확신도: 상/중/하
- 테스트 가능성: 테스트 1개로 옮길 수 있는가? 불가하면 이유

분류해서 출력:

A. 승격 추천   근거 명확 + 관측 가능
B. 보류        근거 불명. 내가 답할 수 있도록 질문 형태로 제시
C. 기각 추천   구현 세부. 이유 명시
D. 신규 제안   명세 누락 후보 기반. 내 결정 필요

자체 검증:
각 BR에 대해 "이게 왜 있는가"를 한 문장으로 답할 수 있는가?
답할 수 없으면 A가 아니라 B다.
이 필터 하나가 대부분의 잘못된 BR을 걸러낸다.

임계값·설정값은 BR 문장에 박지 말고 별도 파라미터 표로 뺄 것.

작성 후 멈추고 내 승인을 기다려. 다음 Phase로 넘어가지 마.
```

---

## 사람이 하는 일

| 분류 | 할 일 | 소요 |
|---|---|---|
| A | 훑고 승인 / 문장 다듬기 | 빠름 |
| B | 질문에 답하거나 `unknowns.md`로 보류 | 대부분의 시간 |
| C | 기각 이유 확인 (가끔 반전이 있다) | 빠름 |
| D | 신규 BR 채택 여부 결정 | 중간 |

체크박스 찍는 수준이지만 **B가 이 작업의 본체**다. 답할 수 없는 것을 억지로 확정하지 말고 보류로 넘겨라. 보류 목록 자체가 조직에 보고할 발견이다.

## 자주 나오는 판정 실수

**if문 하나 = BR 하나가 아니다.** 코드에 분기가 12개여도 사용자가 인지하는 결과가 3가지면 BR은 3개다. 분기를 따라가며 BR을 만들면 코드 구조를 그대로 베낀 명세가 되고, 리팩토링하면 전부 깨진다.

**인프라 결정은 BR이 아니지만 그 이유는 BR이다.** "싱글톤으로 관리한다"는 기각, "여러 화면에서 같은 세션 상태를 본다"는 승격.

**예외 경로는 대부분 BR이다.** 정상 흐름보다 우선해서 검토할 것.

상세 사례는 `docs/br-criteria.md` 참조.

## 승인 후

승인된 BR만 Phase F로 넘긴다. 보류 항목은 `templates/unknowns.md` 형식으로 `spec/unknowns.md`에 누적한다.
