# Phase G — 실행 → 불일치 분석 ★ 사람 판단 필수

**목적**: 명세와 실제 코드의 일치를 확인하고, 어긋난 지점을 찾아낸다.
**주체**: AI가 분석, **사람이 판단**. 여기서 멈춘다.

**이 Phase에서 테스트 실패는 고쳐야 할 문제가 아니라 발견해야 할 성과다.**

---

## 프롬프트

```
작성한 테스트를 기존 코드에 실행하고 결과를 분석해줘.

실패한 테스트마다:
- 어떤 BR인가
- 기대 vs 실제
- 원인 분류 제안:
  (a) BR 문장이 실제 동작과 다름 → 문서 수정 필요
  (b) 테스트 작성 오류 → 테스트 수정
  (c) 실제 코드 버그 → 이슈 등록 대상
  (d) 판단 불가 → 내 확인 필요

(c)로 판단한 경우 추가로:
- 사용자에게 어떤 영향이 있는가
- 과거 이슈 중 유사한 것이 있는가
- 재현 조건

절대 금지:
- 코드를 고치지 마라
- 테스트를 통과시키려고 어서션을 완화하지 마라
- BR 문장을 실제 동작에 맞춰 임의로 수정하지 마라

불일치 발견이 이 사이클의 최대 성과다.
그것을 지워버리면 작업 전체가 무의미해진다.

분석만 하고 멈춰라.
```

---

## 왜 이 단계가 결정적인가

이것 없이 문서와 테스트를 만들면, "새 코드가 새 설계대로 돈다"는 확인은 되지만 **"기존 동작을 빠짐없이 가져왔다"는 확인이 안 된다.** 두 코드를 잇는 다리가 없는 상태다.

리팩토링 후 시장 이슈가 나는 전형적 구조가 정확히 이것이다. 기존 동작을 명시적으로 붙잡지 않은 채 구조를 바꾸는 것.

## 사람의 판단

| 분류 | 판단 근거 | 처리 |
|---|---|---|
| (a) 문서 오류 | 실제 동작이 더 합리적 | BR 문장 수정 → Phase E로 |
| (b) 테스트 오류 | Fake 설정 실수, 어서션 오류 | 테스트 수정 |
| (c) **코드 버그** | 실제 동작이 사용자에게 해로움 | **이슈 등록** |
| (d) 판단 불가 | 의도를 알 수 없음 | `unknowns.md` |

(c)는 별도로 기록해둔다. **"명세화 과정에서 발견한 버그 N건"은 이 작업의 가치를 설명하는 가장 직접적인 근거**다.

## 빌드가 안 될 때

Phase G까지 가려면 테스트가 실행되어야 하는데, 레거시 환경에서는 여기서 막히는 경우가 있다. 그런 경우:

- Phase A~F까지만으로도 프로세스 자체는 검증된다
- BR 입도, 문서 형식, AI 출력 품질은 그 단계에서 다 드러난다
- 다만 **"검증된 명세"는 아니므로** 문서에 그 상태를 명시할 것

## 통과했다면

전부 통과하는 것도 정상이다. 그 BR들은 검증된 명세가 되었고, 기존 코드와 미래 코드를 잇는 다리가 생긴 것이다. Phase H로 넘어간다.
