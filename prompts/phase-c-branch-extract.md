# Phase C — 분기·조건 추출

**목적**: 대상 UC의 실행 경로에 있는 분기와 조건을 빠짐없이 나열한다.
**주체**: AI 전담. 이 단계는 AI가 사람보다 확실히 정확하다.

---

## 프롬프트

```
대상 UC: <UC-EDIT-01: 편집 화면 진입>
관련 파일: <파일 목록>

이 UC의 실행 경로에 존재하는 모든 분기와 조건을 빠짐없이 나열해줘.

표 형식:
| # | 위치(파일:라인) | 조건 | 분기 결과 | 사용자가 보게 되는 것 | 관측가능 |

"사용자가 보게 되는 것"을 채울 수 없으면 관측가능=N 으로 표시해.
예: null 체크 후 기본값 대입 → 사용자는 동일한 결과를 봄 → N
    캐시 miss 시 DB 조회 → 같은 값을 받음 → N
    다운로드 실패 시 재시도 버튼 표시 → 다른 화면을 봄 → Y

이 칸이 BR 판별의 1차 필터이므로 성실히 채울 것.

별도 섹션으로:
[의심]    이 조건이 왜 있는지 코드만으로는 알 수 없는 항목
[예외경로] try-catch, 타임아웃, 취소, 생명주기 중단, 재진입 처리
[상태]    이 UC가 읽거나 쓰는 공유 상태

규칙:
- BR로 확정하지 마라. 관찰 결과만 적어라.
- 추측으로 의도를 채우지 마라. 그 추측이 그대로 명세가 되어버린다.
  모르면 [의심]에 넣어라.
- 호출 깊이가 3단계를 넘어가면 거기서 멈추고 표시해라.
  대상 UC 밖으로 나간 것일 수 있다.
```

---

## 왜 "사용자가 보게 되는 것"을 강제하는가

이 칸을 채우게 하지 않으면 AI가 구현 세부까지 전부 BR 후보처럼 나열한다. `null 체크 후 기본값 대입` 같은 것들이다.

관측 가능성을 먼저 따지면 Phase E에 넘어가는 후보 수가 절반 이하로 줄고, 남은 것의 질이 높아진다.

## 예외 경로에 주목할 것

`[예외경로]` 섹션이 이 Phase의 핵심 산출물이다.

- 정상 흐름은 QA가 잡는다. **과거 시장 이슈는 거의 전부 예외 경로에서 발생한다.**
- 이런 조건은 코드만 봐서는 왜 있는지 알 수 없어 **리팩토링할 때 가장 잘 사라진다.**

여기를 BR로 붙잡는 것이 이 작업의 핵심 가치다.
