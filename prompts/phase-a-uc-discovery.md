# Phase A — 모듈 스캔 → UC 후보 도출

**목적**: 모듈에 어떤 유스케이스가 있는지 목록화한다. 확정이 아니라 후보 제시.
**주체**: AI 주도, 사람이 묶기/쪼개기/삭제만 지시.

---

## 프롬프트

```
너는 레거시 코드에서 유스케이스를 역추출하는 분석가야.

대상: <모듈 경로>

이 모듈의 진입점(Activity/Fragment/ViewModel/public API/이벤트 핸들러)을 찾고,
사용자 또는 외부 시스템 관점의 유스케이스 후보를 도출해줘.

각 UC마다 표로:
| 제안 ID | 한 줄 설명 | 관련 파일 | 분기·예외 대략 수 | 외부 의존성 |

작성 규칙:
- 클래스 하나 = UC 하나가 아니다. 사용자가 인지하는 목적 단위로 묶어라.
  "EditViewModel"이 아니라 "편집 화면 진입"이다.
- 설명에 클래스명을 쓰지 마라. 클래스명이 필요하다면 그건 UC가 아니라
  구현 단위일 가능성이 높다.
- 내부 유틸리티, 헬퍼, 데이터 변환기는 UC가 아니다.
- 확신이 낮은 항목은 [불확실]로 표시하고 이유를 적어라.
- 외부 의존성은 네트워크/DB/파일/다른 모듈 중 해당하는 것을 적어라.

확정하지 말고 후보로만 제시해. 내가 묶기·쪼개기·삭제를 지시하면 반영해줘.

추가로 마지막에:
- 이 모듈의 책임 경계를 2~3줄로 요약
- 모듈 바깥과 주고받는 것(입력/출력)
```

---

## 출력 예시

| 제안 ID | 설명 | 관련 파일 | 분기 수 | 외부 의존성 |
|---|---|---|---|---|
| UC-EDIT-01 | 편집 화면 진입 및 리소스 확보 | EditViewModel.kt, ResourceRepo.kt | ~14 | 네트워크, 파일 |
| UC-EDIT-02 | 편집 결과 저장 | EditViewModel.kt, SaveUseCase.kt | ~8 | 파일, DB |
| UC-EDIT-03 | [불확실] 편집 취소 및 임시본 정리 | EditViewModel.kt | ~5 | 파일 |

## 사람이 할 일

- 묶기: "1번과 3번은 하나의 UC로"
- 쪼개기: "2번은 저장과 검증이 섞여 있으니 분리"
- 삭제: "5번은 UC가 아님"
- 이름 조정: 사용자 관점 표현으로
