# Phase F — 테스트 작성

**목적**: 확정된 BR을 실행 가능한 명세로 만든다.
**주체**: AI 전담. 사람은 어서션만 검수.

**작업 전 `docs/test-rules.md`를 반드시 읽을 것.**

---

## 프롬프트

```
확정 BR 목록:
<Phase E에서 승인된 것>

대상 코드: <파일>
테스트 프레임워크: JUnit5 + <mockk/kotlin.test 등>
템플릿: templates/spec-test-template.kt

docs/test-rules.md 의 규칙을 읽고 각 BR에 대한 테스트를 작성해줘.

핵심 규칙:
1. 테스트 이름 = BR 문장을 그대로 백틱 함수명으로 (한글 허용)
   테스트 목록이 곧 명세 목록이 되어야 한다
2. @Spec("BR-XXX-NNN") 어노테이션 필수
   문서-테스트 결속의 유일한 연결고리다
3. 어서션은 관측 가능한 결과만 —
   state, 반환값, 외부 호출 발생 여부, 저장된 데이터의 최종 상태
4. mock verify 대신 Fake 객체. 호출 여부가 아니라 상태를 검증
5. assertSame, 인스턴스 동일성, private 필드 접근, 호출 순서 검증 금지
6. BR 하나당 테스트 하나가 기본.
   조건이 복수면 나눠도 되지만 병합은 금지
   (실패 시 어느 BR이 깨졌는지 알 수 없게 된다)
7. 타임아웃 등 시간 의존은 가상 시간으로 제어.
   상수는 테스트에 박지 말고 프로덕션 상수를 참조
8. 필요한 Fake는 함께 작성. 기존 Fake가 있으면 재사용

중요:
이 테스트는 기존 코드에 대해 실행된다.
- 새 설계를 전제한 API를 가정하지 마라
- 존재하지 않는 클래스나 메서드를 쓰지 마라
- 테스트를 위해 프로덕션 코드를 수정하지 마라
- 현재 구조에서 테스트가 불가능하다면 그것 자체가 보고할 발견이다.
  억지로 통과시키지 말고 표시해라

작성 후 자체 점검:
- 이 테스트는 구현을 리팩토링해도 살아남는가?
- 실패하면 어느 BR이 깨졌는지 즉시 알 수 있는가?
- 이름만 읽고 무엇을 보장하는지 이해되는가?
```

## 출력 예시

```kotlin
@Spec("BR-EDIT-012")
@Test
fun `리소스가 없으면 편집을 활성화하지 않고 다운로드를 시작한다`() {
    val repo = FakeResourceRepo(available = mutableSetOf())
    val vm = EditViewModel(repo)

    vm.enter(EditFeature.FILTER)

    assertFalse(vm.state.value.editEnabled)
    assertTrue(repo.downloadStarted(FILTER_PACK))
}
```

## 사람 검수 포인트

전부 읽을 필요는 없다. 이것만 확인한다:

- **어서션이 내부 구조를 보고 있지 않은가** — `assertSame`, private 접근, 호출 순서
- **테스트 이름이 BR 문장과 일치하는가** — 어긋나면 둘 중 하나가 잘못된 것
- **Fake가 실제 동작을 왜곡하지 않는가** — 지나치게 단순화하면 통과해도 의미 없다
