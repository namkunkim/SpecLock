# 신규 요구사항 처리 (명세 구축 이후)

역추출이 아니라 **정방향 사용**이다. 명세가 갖춰진 뒤 신규 요구사항이 들어왔을 때 이 순서로 쓴다.

---

## 1단계 — 영향 분석 (코드를 열기 전)

**이 단계가 명세의 최대 가치다.** 지금까지는 이런 충돌을 코드를 다 짜고 QA에서, 혹은 시장에서 발견했다.

```
신규 요구사항: <내용>

docs/spec/ 전체를 읽고 다음을 분석해줘. 아직 코드는 보지 마.

1. 이 요구사항이 영향을 주는 UC와 BR
2. 기존 BR과 충돌하는 것이 있는가
3. 충돌한다면 어떤 결정이 필요한가
4. docs/spec/unknowns.md 의 미결정 항목 중 이번에 결정해야 하는 것
5. 미명세 영역에 해당하는 부분이 있는가

충돌은 해결하지 말고 제시만 해줘. 결정은 내가 한다.
```

### 출력 예시

```
- UC-PAY-02에 신규 BR 필요
- BR-PAY-021(동일 orderId 재요청 시 서버 미전달)과 충돌
  → 자동 재시도가 중복 요청으로 차단됨
- BR-PAY-034(타임아웃 30초)와 상호작용
  → 3회 재시도 시 최대 90초, 상위 BR-ORD-012의 응답 SLA 위반 가능
```

---

## 2단계 — 스펙 먼저 수정

충돌 해소 방침을 사람이 결정한 뒤 BR을 추가·수정한다.

```
결정 사항: <내용>

이에 따라 docs/spec/uc/UC-XXX.md 를 갱신해줘.
- 신규 BR 추가 (ID 부여)
- 기존 BR에 예외 조항이 필요하면 명시
- 근거와 이력 기재

코드는 아직 건드리지 마.
```

---

## 3단계 — 테스트 먼저

```
새로 추가한 BR에 대한 테스트를 작성해줘.
docs/test-rules.md 규칙을 따를 것.
이 시점에는 실패하는 것이 정상이다.
```

여기가 TDD다. 다만 모듈 전체를 갈아엎으면서가 아니라 **신규 요구사항이 들어온 그 부분에만** 적용된다. 조직적 저항이 없는 형태의 TDD다.

---

## 4단계 — 구현 위임

명세가 있을 때와 없을 때 프롬프트의 성격이 완전히 달라진다.

```
UC-PAY-02의 BR-PAY-025, 026을 구현해.

제약:
- 기존 BR은 전부 유지해야 한다
- test/spec 전체가 통과해야 한다
- L0의 모듈 경계를 벗어나지 마라
- docs/spec/ 은 수정하지 마라. 필요하면 제안만 하고 멈춰라
- 테스트가 실패하면 코드를 고쳐라. 테스트를 고치지 마라
```

**명세 없을 때**: AI가 코드베이스를 뒤지고, 관례를 추측하고, 기존 불변조건을 모른 채 작성한다. 결과물을 사람이 전부 검증해야 한다.

**명세 있을 때**: 지켜야 할 것이 명시적이고 **성공 판정이 기계적**이다. 사람은 "이게 맞나?"를 처음부터 판단하는 대신 "테스트가 다 도나?"부터 확인하고 설계 판단에 집중한다.

---

## 5단계 — 회귀 확인

```bash
./gradlew test --tests '*SpecTest'
./scripts/check-spec.sh <module>/docs/spec/uc <module>/src/test
```

기존 BR 테스트가 깨지면 AI가 기존 동작을 침범한 것이고, **어느 규칙을 어겼는지 BR ID로 즉시 특정된다.**

CI 정합성 검사는 문서에 BR을 추가하고 테스트를 안 썼거나, 문서에 없는 `@Spec` ID가 있을 때 잡아낸다.

---

## 부수 효과

**리뷰가 바뀐다.** PR에 스펙 diff가 같이 올라오니 리뷰어가 "이 코드 뭐지?"가 아니라 "이 규칙 변경이 맞나?"를 본다. 리뷰 품질이 코드 읽기 능력에 덜 의존하게 된다.

**시장 이슈 대응이 빨라진다.** 이슈 리포트를 주고 "어느 BR 위반인가"를 묻는다. 위반 BR이 특정되면 원인 코드 범위가 좁혀지고, 어떤 BR에도 해당하지 않으면 그것은 **명세 누락**이므로 새 BR + 테스트로 추가한다. 같은 이슈가 두 번 나지 않는 구조가 된다.

**구조 개선이 열린다.** BR 테스트로 감싸인 영역은 안전망이 있으므로, 그 안에서의 리팩토링은 "제안"이 아니라 "테스트 통과하면 OK인 작업"이 된다.
