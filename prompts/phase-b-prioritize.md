# Phase B — 우선순위 결정, 첫 UC 선정

**목적**: 어느 UC부터 착수할지 근거를 갖고 정한다.
**주체**: AI 제안, 사람 결정.

---

## 프롬프트

```
아래 UC 후보 목록과 참고 자료를 바탕으로 작업 우선순위를 제안해줘.

[UC 목록]
<Phase A 결과 붙여넣기>

[참고 자료]
- 과거 시장 이슈 목록: <붙여넣기 또는 파일 경로>
- 리팩토링/재설계 중 고생했던 지점: <메모>
- QA에서 반복 지적된 영역: <있으면>

평가 축:
1. 과거 이슈 발생 이력 — 가중치 가장 높음.
   이미 터진 곳이 명세가 가장 필요한 곳이다.
2. 예외 경로 복잡도 — 예외 경로가 많을수록 암묵적 동작이 많다.
3. 테스트 격리 난이도 — 외부 의존이 적을수록 착수가 쉽다.
4. 비즈니스 중요도.

출력:
- 축별 점수표 (각 5점 만점) + 총평
- "첫 UC 추천" 1개와 그 이유

첫 UC 선정 기준:
성과가 아니라 사이클 학습이 목적이다.
이슈 이력은 있되 규모가 작고 격리가 쉬운 것을 우선 추천할 것.
앱 생애주기 전반에 걸친 UC(초기 설정, 마이그레이션, 백그라운드 동기화 등)는
테스트 셋업이 무거우므로 첫 대상에서 제외할 것.
```

---

## 판단 기준

**첫 UC는 작고 만만한 것으로.** 여기서 BR 입도 감각이 잡히고, 이때 나온 산출물이 조직에 보여줄 샘플이 된다. 욕심내면 첫 사이클을 완주하지 못한다.

**두 번째부터는 이슈 이력 순으로.** 첫 사이클을 돌려봤다면 무거운 UC도 감당할 수 있다.

## 참고 자료가 없을 때

과거 이슈 이력을 확보할 수 없다면 git log에서 대체 자료를 만들 수 있다.

```bash
# 이슈 티켓 번호가 붙은 커밋 (프로젝트 컨벤션에 맞게 정규식 조정)
git log --grep='#[0-9]\+' --oneline -- <모듈 경로>

# 파일별 수정 빈도 — 자주 고쳐진 곳이 문제가 많았던 곳
git log --format=format: --name-only -- <모듈 경로> \
  | sort | uniq -c | sort -rn | head -20

# hotfix / revert 커밋
git log --oneline --grep='hotfix\|revert\|긴급' -i -- <모듈 경로>
```

이 결과 자체가 Phase D의 입력 자료로도 쓰인다.
