# SpecLock 도입 전략

기술보다 조직적 제약이 성패를 가르는 경우가 많다. 이 문서는 그 부분을 다룬다.

## 범위: 전체 커버는 목표가 아니다

이 작업은 **끝내는 프로젝트가 아니라 습관**이다.

| 대상 | 범위 | 시점 |
|---|---|---|
| L0 (모듈 조망) | 모듈 전체 | 지금 한 번 |
| L1 (UC별 BR) | 우선순위 순 | 점진 확대 |
| L2 (다이어그램) | 필요할 때만 | 자동 생성 |

L0는 A4 2~3장이라 비용이 작고, "전체를 조망하는 문서"라는 목표에 직결된다. L1은 진짜 비용이 드는 곳이라 전체를 한 번에 하면 반드시 중간에 지친다.

**대상 UC에 해당하는 코드만 읽는다.** 모듈 전체를 스캔하고 시작하려 하면 착수 자체를 못 한다.

명세가 없는 영역은 AI에게 "미명세이므로 변경 전 확인 요청"으로 알리면 된다. 부분 커버리지로도 충분히 작동한다.

## 문서와 테스트를 분리하지 않는다

흔한 실패: UC 5개의 문서를 다 쓰고 나서 테스트로 넘어가는 것. 그러면 그 시점에 "이 규칙은 사실 이렇게 안 돌아가는데?"가 무더기로 나온다.

**UC 단위로 완주한다.** UC 하나당 Phase A~H를 한 바퀴 돌린다. 문서만 앞서가면 검증되지 않은 문서가 쌓인다.

절충의 대상은 **범위이지 결합도가 아니다.**

- 양은 줄인다 — 다루는 UC 개수를 조절
- 묶음은 줄이지 않는다 — 손대는 UC는 문서와 테스트를 반드시 같이

## 기존 테스트 처리

기존 테스트가 무의미해 보여도 **이 워크플로우 안에서 삭제하지 않는다.**

이유는 두 가지다. 첫째, 아무리 얇아도 현재 유일한 회귀 기준선이다. 둘째, 주관적 판단으로 남의 테스트를 지우는 것은 조직적 마찰을 만든다. 특히 리팩토링 신뢰가 이미 손상된 상황에서는 최악의 카드다.

### 순서

```
지우고 새로 쓴다                                      ✗
측정 → 새로 쓴다 → 대체를 증명한다 → 그때 지운다        ✓
```

**1단계 — 측정.** mutation testing(JVM은 PIT)을 돌려 클래스별 mutation score를 기록한다. 커버리지는 높은데 mutation score가 낮으면 **코드를 실행만 하고 검증은 안 하는 테스트**다. 이것은 의견이 아니라 측정치다.

> "제 생각엔 이 테스트들이 별로예요"와
> "이 클래스 커버리지 82%인데 mutation score 19%입니다"는
> 회의실에서 전혀 다른 말이다.

**2단계 — 아무것도 지우지 않고 BR 테스트를 옆에 추가.** 중복이 있어도 상관없다. 비용은 CI 시간 몇 초다.

**3단계 — 대체 증명.** 해당 영역에서 다시 PIT를 돌린다. 기존 테스트를 임시 비활성화해도 mutation score가 떨어지지 않으면 **기여도 0이 증명된 것**이다.

**4단계 — 그때 정리.** "제가 판단하기에"가 아니라 "측정 결과 대체되었고 기여도 0으로 확인됨". 별도 PR로 근거를 남긴다. 이 시점엔 반대할 사람이 없다.

### 지우기 전에 확인할 것

| 유형 | 처리 |
|---|---|
| git blame에 **이슈 티켓 번호**가 나오는 것 | **삭제 금지. BR 승격 후보** — 코드는 볼품없어도 실제 회귀를 방어하고 있으며 "왜 이 규칙이 있는가"의 산 증거다 |
| 깨지기 쉬운 mock 검증 (`verify(repo).save(any())`) | 지우면 순이득. mutation score도 낮고 리팩토링만 방해 |
| 복잡한 테스트 픽스처·빌더 | 테스트는 지워도 픽스처는 새 BR 테스트에서 재사용 가능. 먼저 훑을 것 |

## 이름 사용

두 개의 이름을 상황에 따라 쓴다.

| 용도 | 이름 |
|---|---|
| 저장소, 코드, 개발자 간 대화 | **SpecLock** |
| 조직 보고, 과제 등록 | **동작 명세 기반 회귀 검증 체계** |

문서에서 처음 언급할 때는 둘을 연결한다.

> 동작 명세 기반 회귀 검증 체계(SpecLock)

관리자에게 "SpecLock 도입하겠습니다"는 개인 프로젝트로 들린다. "AI 코드 생성 도입을 위한 동작 명세 기반 회귀 검증 체계를 한 모듈에서 검증하겠습니다"는 조직 과제로 들린다. 같은 것을 가리키지만 받아들여지는 무게가 다르다.

## 프레이밍

**"리팩토링"이라는 단어를 쓰지 않는다.** 조직에서 이미 오염된 단어일 가능성이 높다.

대신 **"AI 코드 생성 도입을 위한 회귀 검증 체계 구축"**. 이것은 프레이밍 조작이 아니라 실제로 그것이 맞고, AI 전환이라는 조직 맥락과 정확히 맞아떨어진다. 관리자 입장에서도 위에 보고할 아이템이 생긴다.

**"내 담당 모듈을 개선하겠다"가 아니라 "AI 개발 전환을 위한 안전한 개발 방법을 하나의 모듈에서 검증하겠다"**로 말한다. 겉보기에는 비슷하지만 조직이 받아들이는 의미가 완전히 다르다. 전자는 개인 리팩토링 프로젝트이고, 후자는 AI 전환 프로젝트다.

## 보고 시점과 재료

**첫 UC 1~2개가 끝났을 때 처음 이야기한다.** 그전엔 개인 작업으로 두는 편이 낫다. 보여줄 게 세 가지 있어야 한다.

1. **실물 샘플** — L1 문서 + 테스트 한 세트
2. **과거 이슈 N건 중 M건은 이 테스트로 사전 검출 가능했다** ← 가장 강력
3. **mutation score before/after**

## 측정 지표

측정 항목이 많으면 실무에서 다 못 채운다. 세 개면 충분하다.

| 지표 | 증명하는 것 |
|---|---|
| 문서-실제 동작 불일치 발견 건수 | 문서화 작업의 가치 |
| **과거 이슈 중 사전 검출 가능했던 비율** | 실질적 회귀 방어력 |
| mutation score 변화 | 테스트 품질 (커버리지보다 반박 불가) |

"AI가 코드를 얼마나 생성했는가"는 측정하지 않는다. 의미 없는 지표다.

## 실패 모드

**AI 초안을 읽지 않고 커밋하는 것.** 그럴듯하게 잘 쓰여 있어서 실제로 자주 일어난다. 필터를 하나 두면 대부분 걸러진다 — **각 BR마다 "이게 왜 있는가"를 한 문장으로 답할 수 있어야 확정.** 답 못 하면 보류.

**AI가 테스트를 고쳐서 통과시키는 것.** `CLAUDE.md`에 "테스트가 실패하면 코드를 고친다. 테스트나 spec을 고쳐서 통과시키지 않는다"를 명시한다.

**첫 UC를 너무 크게 잡는 것.** 사이클 학습이 목적이므로 작고 만만한 것으로 시작한다.

**전부 커버하려는 것.** 미명세 영역을 문서에 명시하고 넘어간다. 빈 곳을 숨기지 않는 편이 안전하다.

## 다음 단계

BR 테스트로 감싸인 영역은 안전망이 있으므로, 그 안에서의 구조 개선은 "리팩토링 제안"이 아니라 **"테스트 통과하면 OK인 작업"**이 된다. 설득 논리가 달라진다.

이 순서로 가면 결과적으로 전면 재설계까지도 도달할 수 있다. 다만 거기서 **시작하지 않고** 명세 → 테스트 → 부분 개선을 거쳐 도달하는 것이다.
