# 왜 SpecLock인가

## 반복되는 실패 구조

레거시 모듈에서 흔히 관찰되는 사이클:

```
신규 기능 추가
      ↓
코드 복잡도 증가
      ↓
리팩토링
      ↓
암묵적으로 존재하던 동작 변경
      ↓
시장 이슈
```

원인은 코드 품질 자체가 아니다. **"이 코드가 실제로 무엇을 보장해야 하는가"가 어디에도 명시되어 있지 않은 상태에서 코드를 수정하고 있다는 것**이다.

AI 코드 생성이 들어오면 이 문제는 완화되지 않고 **증폭된다.** 사람보다 훨씬 빠른 속도로 코드가 바뀌는데, "절대로 바뀌면 안 되는 동작"을 알려주지 않으면 AI도 알 수 없기 때문이다.

## 왜 문서만으로는 부족한가

UC 정의와 클래스/시퀀스 다이어그램은 **구조를 설명하는 문서**다. 코드 변경 시 필요한 것은 **행동 명세**다.

그리고 문서에는 구조적 약점이 있다.

> **문서는 썩어도 조용하다.**

갱신되지 않은 문서는 아무 신호도 내지 않는다. 6개월 뒤 아무도 신뢰하지 않게 되고, 그 시점에는 있으나 마나가 된다.

소스코드에서 문서를 자동 생성하는 도구가 만족스럽지 않은 이유도 여기 연결된다. 자동 생성은 다이어그램 레이어(가장 덜 중요하고 가장 자주 변하는 층)에서 잘 작동하고, 정작 필요한 "왜 이 코드가 이렇게 동작해야 하는가"는 소스만으로 복원할 수 없다. 이것은 특정 도구의 한계가 아니라 **역공학 자체의 한계**다.

## 왜 테스트만으로도 부족한가

커버리지를 올리려고 작성된 테스트는 대개 실제 검증 능력이 없다. 코드를 실행만 하고 어서션이 의미 없거나, 구현 세부를 검증해서 리팩토링을 방해한다.

그리고 테스트만 있으면 **"코드를 읽지 않고 동작을 이해한다"**가 성립하지 않는다. 테스트는 개별 사례이지 전체 조망이 아니다.

## 결합이 답이다

```
문서 ──── BR ID ──── 테스트
     └── CI 검사 ──┘
```

BR(Business Rule)에 ID를 부여하고 테스트가 그것을 참조하면 세 가지가 한꺼번에 해결된다.

**1. 문서 부패가 시끄러워진다.** CI가 양방향 정합성을 검사한다. 문서에 BR을 추가하고 테스트를 안 쓰면 빌드가 깨지고, 문서에서 BR을 지우면 고아 테스트가 드러난다. 문서와 테스트가 같이 늙는다.

**2. 문서 품질이 자동 검증된다.** 규칙을 테스트로 옮겨 적을 수 없다면 그 문서는 모호하게 쓰인 것이다. **테스트 작성이 문서의 컴파일러 역할을 한다.**

**3. AI에게 줄 컨텍스트가 완성된다.** "명세 + 해당 BR의 테스트 + 코드"를 주면 AI가 지켜야 할 경계가 명시적이 되고, 성공 판정이 기계적이 된다.

## AI가 새로운 독자다

문서화의 ROI 계산이 최근 달라졌다. 예전에는 독자가 사람뿐이라 비용 대비 효과가 낮았다. 지금은 독자가 하나 더 생겼다.

AI에게 매번 코드베이스를 처음부터 읽히는 것과, 정리된 모듈 명세를 컨텍스트로 주는 것은 결과 품질이 완전히 다르다. 특히 **"기존에 지켜지던 것을 깨지 않는다"** 측면에서 차이가 크다.

## 3계층 분리

한 문서에 성격이 다른 것을 섞으면 전체가 가장 빠른 변경 주기를 따라가다 결국 갱신되지 않는다.

| 층 | 내용 | 작성 | 변경 주기 | 범위 |
|---|---|---|---|---|
| **L0** | 모듈 목적, 책임 경계, 외부 의존성, UC 목록 | 사람 | 연 1~2회 | 모듈 전체 |
| **L1** | UC별 BR, 플로우, 상태 전이, 데이터 규칙 | AI 초안 + 사람 확정 | 기능 변경 시 | 우선순위 순 확대 |
| **L2** | 클래스/시퀀스 다이어그램 | 코드에서 자동 생성 | 언제든 재생성 | 필요할 때만 |

**"코드 안 보고 동작 이해"는 L0 + L1으로 달성된다.** L2는 보조일 뿐이다. 외부에서 모듈을 이해할 때 실제로 필요한 것은 "이 요청이 들어오면 어떤 규칙에 따라 판단하고 어떤 상태로 가는가"이지 클래스 관계도가 아니다.

L2는 갱신 부담이 크고 이해 기여도가 낮으므로 **자동 생성 → 언제든 버릴 수 있는 것**으로 격하한다.

## 규칙을 아는 것과 이해하는 것은 다르다

BR을 정확히 읽어도 AI가 잘못 판단하는 경우가 있다. 원인은 두 갈래다.

**A. BR이 왜 있는지 모른다.** 근거 칸에 티켓 번호만 있으면, 신규 요구사항이
그 BR과 충돌할 때 완화해도 되는 상황인지 판단할 수 없다. "무엇을 지켜야
하는가"는 알아도 "이 규칙이 얼마나 단단한가"를 모르는 상태다.

**B. BR들 사이의 관계를 모른다.** BR을 UC별로 평평하게 나열하면 두 규칙이
서로를 제약하는 관계가 안 보인다. 자동 재시도(BR-X)가 중복 요청 차단(BR-Y)에
걸리는 것처럼, 각각은 맞는데 함께 두면 충돌하는 경우가 실무에서 자주 나온다.

그래서 UC/BR 문서에는 검증 대상인 BR 문장 외에 다음이 같이 있어야 한다.

| 보강 항목 | 메우는 것 |
|---|---|
| 근거를 한 문장으로 요약 | A — 왜 있는지 |
| 반사실 (더 단순한 대안을 왜 안 썼는가) | A — 얼마나 단단한가 |
| BR 간 상호 제약 표 | B — 서로 어떻게 얽히는가 |
| 상태 전이표 (상태가 있는 UC) | B — 전체 흐름 |
| L0의 도메인 개념 관계 | B — 이 모듈 전체의 그림 |
| L0의 시스템 경계 밖 맥락 | A — 모듈 밖 사정이 설계를 정당화 |

이 여섯은 전부 **텍스트로 기존 L0/L1 문서 안에** 들어간다. 새로운 문서
체계가 아니다. 다이어그램으로 그리고 싶은 유혹이 들 수 있는데, 다이어그램은
git diff가 안 보이고 리팩토링 한 번에 틀려진다 — 정확히 L2가 피하려던
문제를 다시 끌어들이는 것이다. 텍스트 표로도 충분하고, CI 결속에도 유리하다.

## Oracle 문제

코드만 보고 명세를 쓰면 **현재 버그가 정답으로 고정된다.** AI로 테스트를 생성할 때의 최대 함정이다.

그래서 명세를 확정할 때는 반드시 코드 외부 소스와 대조한다. 과거 시장 이슈 이력, 이슈 트래커, QA 테스트 케이스, PR 코멘트, 기획 문서, git blame.

**특히 git log에서 이슈 티켓 번호가 붙은 커밋으로 추가된 조건은 근거가 확실한 BR이며, 동시에 리팩토링 때 가장 잘 삭제되는 종류다.** 코드만 봐서는 왜 있는지 알 수 없기 때문이다. 여기를 붙잡는 것이 이 작업의 핵심 가치다.

## 순서가 결정적이다

명세 작업이 실패하는 전형적 순서:

```
기존 테스트 삭제 → 새 설계 기준 테스트 → 새 코드
                                        ↑
                        기존 동작 보존 확인 불가
```

새 설계를 기준으로 쓴 테스트는 "새 코드가 새 설계대로 돈다"는 확인은 되지만 "기존 동작을 빠짐없이 가져왔다"는 확인이 안 된다. 두 코드를 잇는 다리가 없다.

올바른 순서:

```
기존 테스트 유지
      ↓
기존 동작을 BR로 명시
      ↓
BR 테스트 추가
      ↓
기존 코드에 실행  ← 결정적
      ↓
통과하면 그 BR은 검증된 명세
      ↓
그 다음에 구조를 바꿔도 안전
```

굵게 표시한 단계가 빠지면 모든 것이 무너진다. Phase G가 이것이다.

## 조직적 관점

이 워크플로우가 실행 가능한 이유는 기술적인 것이 아니라 **정치적**이다.

**프로덕션 코드를 건드리지 않는다.** 반대할 명분이 없다. 실패해도 손실이 0이고, 성공하면 다음 단계를 제안할 자격이 생긴다.

**"리팩토링"이 아니라 "AI 코드 생성 도입을 위한 회귀 검증 체계"다.** 이것은 프레이밍 조작이 아니라 실제로 그것이 맞다.

**측정 가능한 성과가 나온다.** 특히 "과거 이슈 N건 중 M건은 이 테스트로 사전 검출 가능했다"는 가장 설득력 있는 단일 지표다.
