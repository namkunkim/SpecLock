## 정의

**BR(Business Rule)**: 모듈이 반드시 지켜야 하는 동작 약속을, 하나의 문장으로 검증 가능하게 적은 것.

구현이 바뀌어도 그대로 남아야 하는 것. **"어떻게"가 아니라 "무엇을 보장하는가"**.

BR은 새로 발명하는 것이 아니라 **이미 코드 안에 암묵적으로 존재하는 것을 꺼내 적는 것**이다.

## 판별 질문 2개

### Q1. 이것만 어겼을 때 사용자가 알아차리는가?

| 상황 | 판정 |
|---|---|
| 5분 캐시 유효기간을 안 지킨다 | 사용자가 오래된 값을 봄 → **BR** |
| LruCache 대신 HashMap을 쓴다 | 사용자는 모름 → BR 아님 |
| 캐시 miss 시 DB 조회 | 같은 값을 받음 → BR 아님 (경로일 뿐) |

### Q2. 테스트 한 개로 옮길 수 있는가?

옮길 수 없다면 문장이 모호하거나 여러 규칙이 뭉쳐 있다. 쪼개거나 다시 쓴다.

```
✗ assertSame(a, b)                        인스턴스 동일성 = 구현 검증
✓ 화면 A에서 갱신한 값이 화면 B에서 보인다   행동 검증 = BR
```

## 사례별 판정

### 1. 인프라·생명주기 결정 (싱글톤, DI 스코프)

**결정 자체는 BR이 아니다.** 그러나 **그 결정이 보장하려는 것**은 BR이다.

```
✗ BR-XXX-001: PaymentManager는 싱글톤으로 관리한다
```

싱글톤을 팩토리로 바꿔도 사용자가 모른다면 BR이 아니다. 이렇게 적으면 DI 스코프 변경 시 테스트가 깨져 리팩토링을 방해한다.

"왜 싱글톤이어야 하는가"를 파고들면 BR이 나온다:

| 싱글톤을 쓰는 이유 | BR 문장 |
|---|---|
| 상태 공유 | 여러 화면에서 같은 세션 상태를 본다 |
| 커넥션 단일성 | 동시에 2개 이상의 소켓 연결을 열지 않는다 |
| 캐시 유지 | 화면 전환 후에도 조회 결과를 재사용한다 |
| 초기화 비용 | 앱 생애주기 동안 초기화를 1회만 수행한다 |

반대로 **"매번 생성해야 한다"**는 BR일 수 있다:

```
BR-XXX-005: 요청마다 독립된 컨텍스트를 사용하며 이전 요청의 상태가 남지 않는다
```

상태 오염이 실제 버그로 이어지고 테스트 가능하기 때문이다.

**결정 자체를 적을 곳**: L0의 책임 경계 항목, `decisions.md`(ADR), 또는 적지 않음. 새 코드가 따라야 할 관례라면 `CLAUDE.md` 쪽이 적합하다. BR 목록에 구현 관례를 섞으면 목록이 오염되고 CI 검사의 의미가 흐려진다.

### 2. 세부 조건·분기

**BR인 것** — 조건 자체가 비즈니스 판단:

```
BR-PAY-031: 결제 금액이 임계액을 초과하면 추가 인증을 요구한다
BR-PAY-032: 인증 실패가 3회 누적되면 일정 시간 시도를 차단한다
BR-PAY-033: 네트워크 오류로 실패한 경우에만 자동 재시도하고
            서버가 거부한 경우는 재시도하지 않는다
```

`033`이 좋은 예다. "왜 이 분기가 있지?"의 답이 **"이렇게 하지 않으면 사용자에게 문제가 생겨서"**라면 BR이다.

**BR이 아닌 것** — 같은 결과를 내기 위한 내부 처리:

```
✗ null 체크 후 기본값을 넣는다
✗ 리스트가 비어있으면 early return
✗ 캐시 miss 시 DB 조회
```

### 3. 임계값과 설정값

조건은 BR이지만 **임계값은 BR 문장에 박지 않는다.**

```
BR-PAY-031: 고액 결제 시 추가 인증을 요구한다   ← 규칙
            임계값: 50만원 (설정값, 변경 가능)    ← 파라미터
```

테스트도 값이 아니라 **"임계 초과 시 인증 요구"**를 검증한다. 값을 박아넣으면 정책 하나 바뀔 때마다 문서와 테스트를 전부 고쳐야 한다.

### 4. 예외·에러 경로

**대부분 BR이다. 그리고 실무에서 가장 중요하다.**

```
BR-PAY-041: 결제 진행 중 앱이 종료되어도 재진입 시 진행 상태를 복원한다
BR-PAY-042: 서버 응답이 타임아웃되면 서버 측 처리 여부를 별도 조회로 확인한다
```

이유:

- 정상 흐름은 QA가 잡는다. **과거 시장 이슈는 거의 전부 예외 경로에서 발생한다.**
- 이런 조건은 코드만 봐서는 왜 있는지 알 수 없어 **리팩토링할 때 가장 잘 사라진다.**

여기를 BR로 붙잡는 것이 이 작업의 핵심 가치다.

### 5. 리소스·선행조건

"리소스가 있도록 해야 한다" 같은 문장은 **아직 BR이 아니다.** "없으면 어떻게 되는가"가 빠져 있고, 사고는 정확히 거기서 난다.

한 문장에 최소 세 가지 결정이 압축되어 있으므로 펼친다:

```
BR-EDIT-011: 진입 시 해당 기능의 필수 리소스 존재를 확인한다
BR-EDIT-012: 미확보 시 기능을 활성화하지 않고 다운로드를 시작한다
BR-EDIT-013: 다운로드 중에는 진행 상태를 표시하며 화면을 유지한다
BR-EDIT-015: 실패 시 화면을 종료하지 않고 재시도 수단을 제공한다
```

**선행 UC에서 이미 처리했는데 여기서 또 확인한다면, 그 이유를 근거로 남긴다.** 남기지 않으면 다음 사람이 "앞에서 받았으니 불필요하다"며 지운다.

```
BR-EDIT-014: 초기 설정 완료 여부와 무관하게 진입 시점에 리소스 존재를 확인한다
  근거: 저장공간 부족으로 인한 삭제, 앱 데이터 삭제, 리소스 버전 갱신 가능
  이력: 시장 이슈 #12847
```

대체 수단이 있다면 각각이 사용자에게 다른 결과를 주므로 별도 BR이다. 폴백("다른 것을 보여준다")과 우선순위 변경("같은 것을 더 빨리 준다")은 결코 같은 문장이 될 수 없다.

## 입도(Granularity) 기준

**if문 하나 = BR 하나가 아니다.**

코드에 분기가 12개여도 사용자가 인지하는 결과가 3가지면 BR은 3개다. 분기를 따라가며 BR을 만들면 **코드 구조를 그대로 베낀 명세**가 되고, 리팩토링하면 전부 깨진다.

기준: **이 규칙 하나만 어겼을 때 사용자가 인지할 수 있는가.** 그 단위가 BR 하나다.

## 문장 작성 규칙

- 한 문장. 접속사로 두 규칙을 잇지 않는다
- 현재형 서술. "~해야 한다"보다 "~한다"
- 클래스명·메서드명·자료구조 언급 금지
- 주어는 시스템, 목적어는 관측 가능한 결과
- 근거가 이슈면 티켓 번호를 병기한다. 이유 없는 규칙은 반드시 다시 삭제된다

## 판단이 안 될 때

근거를 못 찾는 조건은 **지우지도 확정하지도 말고** `spec/unknowns.md`에 모은다. 나중에 팀에 물어보거나 git blame으로 추적할 대상이며, 이 목록 자체가 조직에 보고할 만한 발견이다.
