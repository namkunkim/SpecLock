## 시스템 경계 밖 맥락

이 모듈 자체가 아니라 "왜 이렇게 설계됐는가"를 결정하는 바깥 사정.
이게 없으면 AI가 방어적으로 짜인 코드를 "과하다"고 판단해 단순화해버린다.

- <예: 이 앱은 오프라인 우선으로 설계됨 — 사용자 다수가 저사양·저대역폭 환경>
- <예: 이 데이터는 서드파티가 제공하며 신뢰할 수 없는 입력으로 취급>

## 목적

## 도메인 개념 관계

용어집은 "이게 무엇인지"는 알려주지만 "개념들이 서로 어떻게 얽혀 있는지"는
알려주지 않는다. 이게 없으면 BR을 하나하나는 맞게 읽어도, 명세되지 않은
빈 곳을 도메인 규칙에 안 맞게 채워버린다. 다이어그램이 아니라 텍스트로
충분하다 — git diff가 보이고 굳이 재생성할 필요가 없다.

- <예: A가 삭제되면 그 A에 속한 B는 로컬에 남지만 신규 C 조회는 불가능해진다>
- <예: B는 여러 A에서 동일 항목으로 매칭될 수 있다 (병합 대상)>

## Use Case 목록

**명세 상태를 반드시 표시한다.** 미착수 UC가 있는 것은 정상이며, 숨기지 않아야 AI와 다음 작업자가 "이 영역은 명세되지 않았다"를 알고 임의 판단하지 않는다.

## 주요 상태

이 모듈이 유지하는 상태와 생명주기. 화면 간 공유되는 것, 프로세스 종료 시 사라지는 것, 영속되는 것을 구분한다.

| 상태 | 범위 | 생명주기 | 관련 UC |
|---|---|---|---|
| | 화면 / 세션 / 앱 / 영속 | | |

인프라 결정(싱글톤, DI 스코프 등)이 이 표의 "범위"와 "생명주기"를 보장하기 위한 것이라면, 그 결정 자체가 아니라 **보장하려는 내용**을 여기 적는다. 상세는 `docs/br-criteria.md` 참조.
